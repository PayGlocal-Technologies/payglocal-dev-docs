Partner APIs: Merchant onboarding

Partner Onboarding API v1

Onboard a merchant to PayGlocal end to end: create the merchant, submit KYC and KYB data, configure products and fees, upload documents, and hand over to the merchant for verification.

This is the standard contract for every new partner integration.

Roles

ActorResponsibility
PartnerCreates the merchant, submits business details, authorised signatory, beneficial owners, settlement bank account, products and documents, and issues the merchant link.
MerchantEnd customer who wants to enable payments for their business. Opens the merchant link, verifies the signatory through the generative link and video KYC, confirms the details and accepts the terms. Responds to any pendency on the same link.
PayGlocalValidates each submission, raises pendencies where clarification is needed, reviews each product and activates its MID.

Integration flows

The {flow} path segment selects how the merchant is onboarded.

Flow{flow}How it worksexternalOnboardingId
Merchant completesonboardThe partner submits the data; the merchant completes verification on the link.Mandatory
Partner assistedassisted-onbThe partner’s team completes the details with the merchant; issuing the link hands the onboarding over to the merchant.Optional
 
sequenceDiagram
  participant P as Partner
  participant G as PayGlocal API
  participant M as Merchant
  P->>G: 1. POST /initiate
  G-->>P: orgId
  P->>G: 2. PUT business, signatory, owners
  P->>G: 3. PUT bank details and products
  P->>G: 4. Upload documents
  P->>G: 5. PUT /redirect
  G-->>P: Merchant link
  P->>M: 6. Share the merchant link
  M->>G: 7. Verify, confirm, accept terms
  G-->>P: Webhooks (verification, terms, VKYC)
  G-->>M: 8. Pendency raised, status NEEDS_ACTION
  M->>G: Clarification on the same link
  P->>G: Resolve items via needs action APIs
  G-->>P: 9. PRODUCT_STATUS_UPDATED (LIVE)

The partner drives every step until the merchant link is issued. After that, the merchant and PayGlocal act, and the partner tracks progress through webhooks and the status API. Every response carries nextAction, naming the next step.

Getting started

All v1 requests go over HTTPS to the PayGlocal API gateway and are authenticated with your partner credentials.

PayGlocal issues UAT credentials at kickoff and production credentials after UAT sign-off.

Authentication

Every request to the gateway carries the following headers.

HeaderDescription
x-gl-authPartner API key. The gateway identifies the partner from this key; never send a partner ID in the body.
x-gl-digestBase64-encoded HMAC-SHA256 of the signing input, keyed with your API secret.
Content-Typeapplication/json on every POST and PUT

The signing input is the exact raw body for POST and PUT requests, and the request path including any query string for GET requests (no host or scheme). Any change to the body after signing, including whitespace or field order, returns HTTP 401. Always sign with the API secret, never the API key, and send the digest as Base64, never hex. See Authentication.

The file upload to a presigned URL goes directly to storage, not the gateway. Do not send x-gl-auth or x-gl-digest on that request.

Every response uses a common envelope. Endpoint samples in this reference show the data object only.

FieldReturned onDescription

Conventions

  • Naming and time. Field names are camelCase. Timestamps are ISO 8601 in UTC.
  • Partial updates. Every PUT is a partial update. Send the fields you have and resend a field to correct it. Unrecognised fields are ignored, not rejected, so check field names carefully.
  • Write responses. Every write returns orgId, onboardingStatus and nextAction. Call the status API for the full record.
  • Rejected requests. A rejected request saves nothing. Correct the named field and resend.

Onboarding lifecycle

Three fields track progress: onboardingStatus for the merchant, productStatus for each product, and nextAction for the next step.

Merchant onboarding: documents

Get upload URL

Documents are never sent in an API body. Each document is uploaded in three steps.

  1. Get a one-time upload URL (this endpoint).
  2. Upload the file directly to that URL, with no gateway headers.
  3. Poll the upload status until it is COMPLETED. The document is then linked to the merchant.
PUT…/merchant/{flow}/{orgId}/document/upload-url

Request fields

Uploading the file

Send PUT {presignedPutUrl} with the file as the raw binary body and every metaData entry as a request header, exactly as returned. Do not send x-gl-auth or x-gl-digest. An empty HTTP 200 response confirms the file is stored.

Needs action

Get needs action

Lists what is blocking the merchant’s approval and how to resolve each item. Each item names the products it blocks and, where you can act, the exact inputs to render.

GET…/merchant/dashboard/{orgId}/needs-action

No request body. The path uses dashboard where the onboarding endpoints use {flow}; headers and authentication are the same as every other endpoint.

Poll every 5 seconds while any item is PROCESSING or any product is INITIATED or IN_PROGRESS, and stop otherwise. An empty actionItems list while a product is IN_PROGRESS means a check is running, not that the merchant is clear.

Rendering rules

  • Products. Show each product’s state. A product in MANUAL_REVIEW is with PayGlocal and lists no item.
  • Order. Render actionItems in the order received, grouped by group if the design needs it.
  • Inputs. TEXT and URL are text boxes. SELECT is a drop-down that sends value. CHECKBOX sends true when ticked. FILE is an uploader limited to acceptedDocumentTypes.
  • Alternatives. Two inputs that name each other in alternativeTo are one question. Ticking the checkbox clears the select, and the reverse. Mark neither as mandatory on its own.
  • No resolution. An ACTION_REQUIRED item with no resolution is a link the person completes on their own, such as an address check or video KYC. Ask the user to share it with subject.name.
  • Processing. Show a progress state and keep polling.
  • Identifiers. Never branch on actionItemId. Use status, resolution.type and the inputs.
  • Optional fields. Treat missing optional fields as absent, not empty. Inputs do not carry current values, so corrections cannot be pre-filled.

Needs action

Answer needs action

Sends the answer to one open action item. PayGlocal checks it against the live list, applies it with the same checks as the onboarding APIs, and returns the fresh needs-action view.

PUT…/merchant/dashboard/{orgId}/needs-action

Answer one item per call, with all of that item’s inputs together. Render the next item straight from the response.

Request fields

FieldRequirementFormatDescription
actionItemIdMandatoryString, exactly as listedItem being answered. Sent in the body, never in the path.
answers[]MandatoryArrayOne entry per input of the item. Empty only for an item with no inputs (RECHECK).
answers[].fieldIdMandatoryStringThe input’s fieldId from Get needs action
answers[].valueConditionalStringMandatory for TEXT, URL and SELECT inputs. A SELECT value must be one of the offered options.
answers[].isCheckedConditionalBoolean, trueFor a CHECKBOX input. Sent only when ticked.

Items answered here

ItemAnswersResult
ENTITY_TYPEentityTypeSaved immediately. CIN_LLPIN may appear next.
CIN_LLPINcin or llpInPROCESSING while the registry lookup runs
GST_ANSWERgst or noGstCheck, exactly oneThe item clears when the GSTIN is active and verified; otherwise it stays.
PANpanNumberOnly before the details are confirmed. PROCESSING while the lookup runs.
RISK_* with a URL inputThe page URLThe website check reruns in the background. The product is IN_PROGRESS and risk items leave the list until it ends.
RISK_WEBSITE_LIVENone (answers is empty)Every website check reruns in the background.

Document items are resolved through Get upload URL. Person links (PERSON_ADDRESS, VKYC) are completed by the person. Every other item is not yet answerable here and is rejected with ACTION_ITEM_NOT_ANSWERABLE.

Notes

  • One call at a time. Two calls for the same merchant at the same moment can conflict. The losing call returns HTTP 409; call Get needs action and resend.
  • Website rechecks. Each risk answer counts as one resubmission round. After 3 rounds, the product moves to PayGlocal review (MANUAL_REVIEW) and further risk answers are rejected.
  • No registry wait. A GSTIN the registry does not know, or a PAN that does not match, is saved and the item stays open.

Errors: ACTION_ITEM_NOT_OPEN, ACTION_ITEM_NOT_ANSWERABLE, FIELD_NOT_ASKED, ANSWER_REQUIRED, TWO_ANSWERS, OPTION_NOT_OFFERED, KYC_DECIDED, KYC_FROZEN, plus the field errors of the matching onboarding API, such as ENTITY_TYPE_NOT_ALLOWED, GSTIN_NOT_OF_PAN and GST_OR_UDYAM_REQUIRED

Webhooks

Delivery and handling

PayGlocal sends a signed JSON POST to your webhook URL when the merchant acts or a product changes status.

Treat each event as a trigger: on receipt, call merchant status for the full record. PayGlocal registers your webhook URL and subscribed events during setup.

eventTypeSent when
MERCHANT_VERIFICATION_COMPLETEDThe merchant confirms the details on the merchant link.
MERCHANT_TNC_ACCEPTEDThe merchant accepts the terms and conditions.
MERCHANT_VKYC_COMPLETEDThe signatory’s video KYC is complete.
PRODUCT_STATUS_UPDATEDA product’s status changes.

Common payload fields

FieldDescription
eventTypeEvent name
orgIdMerchant identifier
externalOnboardingIdYour reference for the merchant
onboardingStatusOnboarding status when the event occurred
occurredAtEvent time, ISO 8601 in UTC

Handling rules

  • Verify the signature on every event before acting on it.
  • Acknowledge with HTTP 2xx promptly and process the event asynchronously.
  • Deduplicate. An event can be delivered more than once. Key your handler on orgId, eventType, product and occurredAt.
  • Action items are not sent as webhooks. List them with Get needs action.

Fee rules

  • Each fee has a feeType (FIXED or PERCENTAGE) and a fee value.
  • feeType must match the type set in your partner pricing for that fee.
  • fee must sit within your partner pricing range, with at most 4 decimal places.
  • Send exactly one fee block for each selected product, and none for products not selected.

Compliance and go-live

Data handling

PayGlocal operates under RBI PA-CB and PA-O authorisation, PCI DSS and the DPDP Act, and partners must handle merchant data to the same standard.

  • Test data. Use only UAT test identities in UAT. Never place a real PAN, Aadhaar or bank account number in test tools, screenshots or tickets.
  • Masking. Mask PAN and bank account numbers in logs and UI. Never log API secrets, digests or presigned URLs.
  • Minimal storage. Store only what you need to operate: orgId, externalOnboardingId, statuses and MIDs.
  • Secrets. Keep the API secret server-side and rotate it immediately if exposed.
  • Merchant links. Send merchant links only to the merchant’s verified contact.

Go-live checklist

  • HMAC digest verified on GET, POST and PUT in UAT
  • End-to-end flow passed for a private limited company and a proprietor
  • Every partner-facing error code handled and surfaced to your users
  • Document upload round trip passed, including the scan wait
  • Webhook endpoint verifies signatures and is idempotent
  • Pendency loop tested through status polling
  • Fees confirmed within the agreed pricing range
  • Production credentials and webhook URL registered
