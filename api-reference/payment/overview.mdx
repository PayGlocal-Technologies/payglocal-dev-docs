## Authentication

All Payment APIs use **JWS + JWE** authentication (different from Onboarding API's HMAC-SHA256).

| API Area | Auth Mechanism | Key Header |
|---|---|---|
| Merchant Onboarding | HMAC-SHA256 (`x-gl-digest`) | `x-gl-auth` |
| Payment / SI APIs | RSA-signed JWS + JWE-encrypted body | `x-gl-token-external` |

<Warning>
  Do not mix credentials between Onboarding and Payment APIs.
</Warning>

---

## Request Format

Most payment requests require encryption and signing:

```
Raw JSON Payload
      ↓
[ generateJWE ]  ← Encrypts with PayGlocal's PUBCERT
      ↓
  JWE Token (request body)
      ↓
[ generateJWS ]  ← Signs with your PVT-KEY
      ↓
  JWS Token (x-gl-token-external header)
```

**HTTP Request Structure:**
```
POST https://api.uat.payglocal.in/<endpoint>
Content-Type: text/plain
x-gl-token-external: <generated-jws-token>

<generated-jwe-payload>
```

See [Payment Flow](/merchant/payment-flow) for implementation details.

### Status API Exception (GET)

Status check does not send a JWE body. Build the path string and sign it to create JWS:

```javascript
const { jwsToken } = generateJWS(
  statusPayload="/gl/v1/payments/<TXN-GID>/status",
  pvtKey,
  merchantId,
  pvtKeyId
);
```

Use this JWS in `x-gl-token-external` for `GET /gl/v1/payments/<TXN-GID>/status`. See [Status API](/api-reference/payment/get-status) for details.

## Required Credentials

| Credential | Source | Purpose |
|---|---|---|
| PayGlocal Public Certificate (PUBCERT) | GCC → Key Management | Encrypts payload (JWE) |
| Your Private Key (PVT-KEY) | GCC → Key Management | Signs request (JWS) |
| Merchant ID (MID) | Provided at onboarding | Embedded in token headers |
| Public Key ID (pubKeyId) | PUBCERT filename | Identifies encryption key |
| Private Key ID (pvtKeyId) | PVT-KEY filename | Identifies signing key |

<Tip>
  **Extract Key IDs:** The Key ID is the part before the underscore in the filename.  
  - `884hiurh-8e0b-4907-38nn-fuerikejr89_paygmerchant.pem` → `884hiurh-8e0b-4907-38nn-fuerikejr89`
</Tip>

See [Key Management](/getting-started/dashboard-and-key-management) for setup instructions.

## Transaction Identifier (GID)

Every API response returns a **GID** (PayGlocal ID) — the primary transaction reference:

- Format: `gl-13bbd3c4-9817-4786-96c6-12fa6191f118`
- Returned on payment initiation
- Used as `{gid}` path parameter in status, refund, capture, and reversal calls
- Your `merchantUniqueId` can be used interchangeably in most endpoints

```
GPI Initiation → Returns: gid
        │
        ├── GET  /gl/v1/payments/{id}/status
        ├── POST /gl/v1/payments/{gid}/refund
        ├── POST /gl/v1/payments/{gid}/capture
        └── POST /gl/v1/payments/{gid}/auth-reversal
```

## API Endpoints

### Regular Payment

| Endpoint | Method | Use Case |
|---|---|---|
| [POST /gl/v1/payments/initiate/paycollect](/api-reference/payment/gpi-paycollect) | POST | **PayCollect** (default) — Non-PCI merchants. PayGlocal hosts checkout. |
| [POST /gl/v1/payments/initiate](/api-reference/payment/gpi-initiate) | POST | **PayDirect** — PCI-certified merchants. You collect card data. |

### Transaction Management APIs

| Endpoint | Method | Use Case |
|---|---|---|
| [GET /gl/v1/payments/{id}/status](/api-reference/payment/get-status) | GET | Check payment or refund status |
| [POST /gl/v1/payments/{gid}/refund](/api-reference/payment/refund) | POST | Issue full or partial refund |

### Auth and Capture APIs

| Endpoint | Method | Use Case |
|---|---|---|
| [POST /gl/v1/payments/initiate](/api-reference/payment/auth-payment-initiation) | POST | **Post-authorization initiation** — Hold funds only (`captureTxn: false`). PayDirect path. |
| [POST /gl/v1/payments/{gid}/capture](/api-reference/payment/standalone-capture) | POST | Capture authorized payment |
| [POST /gl/v1/payments/{gid}/auth-reversal](/api-reference/payment/standalone-reversal) | POST | Void authorized payment |

<Note>
  Auth and Capture requires special MID configuration. Contact [merchant.support@payglocal.in](mailto:merchant.support@payglocal.in).
</Note>

### Recurring Payment APIs

| Endpoint | Method | Use Case |
|---|---|---|
| [POST /gl/v1/payments/initiate/paycollect](/api-reference/standing-instructions/si-payment-initiation) | POST | Create SI mandate with first payment (Fixed or Variable) |
| [POST /gl/v1/payments/si/sale](/api-reference/standing-instructions/si-subsequent-payment) | POST | Charge against active mandate (Variable / on-demand) |
| [POST /gl/v1/payments/si/status](/api-reference/standing-instructions/si-status) | POST | Retrieve mandate status and history |
| [PUT /gl/v1/payments/si/status](/api-reference/standing-instructions/si-cancellation) | PUT | Pause, activate, or cancel mandate |

## Payment Processing Models

Your MID is configured for one of two models:

| Model | Behavior | Next Action |
|---|---|---|
| **Auth + Capture** (default) | Payment authorized and captured automatically after 3DS | Poll status; fulfill on `SENT_FOR_CAPTURE` |
| **Auth Only** | Only 3DS authentication completes | Send separate Capture or Reversal call |

Contact merchant support to configure your model.

## Callback Handling

After payment completion, PayGlocal POSTs the result to your `merchantCallbackURL` as an encoded JWT (`x-gl-token`).

```
PayGlocal processes payment
      ↓
POST to merchantCallbackURL
Body: x-gl-token=<jwt>
      ↓
Decode JWT (split on ".", take index [1], base64url-decode)
      ↓
{ "status": "SENT_FOR_CAPTURE", "gid": "...", "amount": "..." }
```

See [Payment Response Handling](/merchant/payment-response-handling) for implementation.
