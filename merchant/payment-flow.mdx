<Note>This page covers token construction — the cryptographic step that happens on your server before each API call. For the full payment lifecycle (redirect, callback, settlement), see [Payment Initiation Flow](/integration/payment-flow).</Note>

## Overview

Every PayGlocal Payment API request requires the body to be prepared in the following sequence:

1. Serialize the payload to a JSON string
2. For PayDirect card payments: JWE-encrypt the card data sub-object using PayGlocal's public certificate
3. JWS-sign the full payload using your RSA private key
4. Send the resulting token as the `x-gl-token-external` request header

## Credentials Required

| Credential | Where to Get | Used For |
|---|---|---|
| RSA Private Key | [Download from GCC](/set-up/keys/private-key) | JWS signing |
| PayGlocal PUBCERT | [Download from GCC](/set-up/keys/public-certificate) | JWE encryption (PayDirect card data) |
| Merchant ID | GCC TID Details | `x-gl-merchantid` header |
| Key ID (KID) | Extracted from private key filename | `x-gl-kid` header |

## Why Two Tokens?

| Token | Sent as | Key used | What it protects |
|---|---|---|---|
| **JWE** | Request body | PayGlocal's **public** certificate | Confidentiality — payload is unreadable in transit |
| **JWS** | `x-gl-token-external` header | **Your** RSA private key | Authenticity — PayGlocal confirms the request originated from you |

One without the other is incomplete. JWE alone means PayGlocal can read the data but cannot trust its origin. JWS alone means PayGlocal can verify the sender but cannot read the payload.

## Token Construction Functions

### `generateJWE` — Encrypt the Payload

**Input:** Payment payload + PayGlocal's public certificate + Merchant ID + Public Key ID

**What it does:** Converts the JSON payload into a compact encrypted token. The data is unreadable in transit — only PayGlocal can decrypt it using their private key.

**Output:** A JWE token — the encrypted string that becomes the **body of your API request**.

---

### `generateJWS` — Sign the JWE

**Input:** JWE token + your RSA private key + Merchant ID + Private Key ID

**What it does:** Takes the JWE token, computes a SHA-256 hash, and signs it with your private key. This signature proves the request was sent by you and has not been modified in transit.

**Output:** A JWS token — the signed string sent in the **`x-gl-token-external` request header**.

---

### `generateJWEAndJWS` — Combined Entry Point

**Input:** Payload + all five credentials (public certificate, private key, Merchant ID, Public Key ID, Private Key ID)

**What it does:** Validates all credentials, calls `generateJWE`, then passes the result to `generateJWS` automatically.

**Output:** Both tokens — `{ jweToken, jwsToken }`.

<Tip>This is the only function you need to call directly. `generateJWE` and `generateJWS` run internally.</Tip>

## Request Assembly

Once you have both tokens, assemble the request:

```
POST  https://api.uat.payglocal.in/gl/v1/payments/initiate/paycollect

Content-Type: text/plain
x-gl-token-external: <JWS Token>
x-gl-merchantid: <MERCHANT_ID>
x-gl-kid: <KEY_ID>

Body: <JWE Token>
```

## Flow Summary

```
Payment Payload (JSON)
         │
         ▼
  [ generateJWE ]
  Encrypt with PayGlocal's public certificate
  → JWE Token (encrypted body)
         │
         ▼
  [ generateJWS ]
  Sign with your RSA private key
  → JWS Token (x-gl-token-external header)
         │
         ▼
  POST /gl/v1/payments/initiate/paycollect
  PayGlocal verifies JWS → decrypts JWE → processes payment
```

## Portfolio / Multi-MID Setup

If operating multiple sub-merchants under a parent MID, include the `x-gl-kid-mid` header with the child MID. See [Request Construction](/set-up/keys/request-construction) for the portfolio configuration.
