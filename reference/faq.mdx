## Authentication

<AccordionGroup>
  <Accordion title="Why am I getting 401 Unauthorized?">
    Check all five common causes in order:

    1. **Wrong signing key** — Are you using the **API Secret** to compute the digest? The API Key and API Secret are different. The digest must be signed with the Secret.
    2. **Digest input mismatch (POST/PUT)** — The digest must be computed over the **exact raw request body bytes** you send. Any difference in whitespace, key ordering, or encoding will cause a mismatch.
    3. **Digest input mismatch (GET)** — For GET requests, compute the digest over the **full URL** including protocol, host, path, and query string.
    4. **Wrong encoding** — The digest output must be **Base64-encoded**, not hex.
    5. **Wrong environment** — Sandbox keys will not work in Production and vice versa.

    See [Authentication](/authentication) for multi-language code examples.
  </Accordion>

  <Accordion title="What is the difference between the API Key and API Secret?">
    - **API Key (`x-gl-auth`)** — A static identifier. Safe to store in environment variables. Not secret.
    - **API Secret** — The signing key used to compute the HMAC-SHA256 digest. Treat like a password. Never expose in client-side code, logs, or version control.

    Both are downloaded from the PayGlocal partner dashboard under **Settings → API Keys**.
  </Accordion>
</AccordionGroup>

## Transactions

<AccordionGroup>
  <Accordion title="What is the difference between GID and merchantUniqueId?">
    - **GID** — Generated by PayGlocal. Always starts with `gl-`. The authoritative identifier for a transaction in PayGlocal's system. Returned in every GPI response.
    - **merchantUniqueId** — Generated by you. Must not start with `gl-`. Your internal reference. Can be used interchangeably with GID in Get Status and follow-on requests.

    Use `merchantUniqueId` as your primary lookup key — it maps to your own order/transaction IDs and survives if you ever need to re-query before receiving the GID (e.g., network timeout on the GPI response).
  </Accordion>

  <Accordion title="Should I rely on the callback or always call Get Status?">
    **Always call Get Status server-side**, regardless of the callback.

    The callback (`x-gl-token` POST to your `merchantCallbackURL`) is the primary notification mechanism, but it can fail — the customer might close the browser, a network error might prevent the redirect, or token validation might fail.

    Your integration must handle this case:
    1. Validate the `x-gl-token` on callback receipt.
    2. If validation succeeds → extract status from the token.
    3. If validation fails or callback never arrives → call `GET /payments/{gid}/status` using the GID from the original GPI response.

    Never fulfill an order based solely on a callback. Always confirm with a server-to-server Get Status call.
  </Accordion>

  <Accordion title="What does SENT_FOR_CAPTURE mean? Is the payment done?">
    `SENT_FOR_CAPTURE` is a **final status** — the payment has been captured and will settle in your merchant account. It is safe to fulfill the order (ship goods, activate subscription, etc.).

    It does **not** mean the funds are already in your bank — settlement typically takes 1-3 business days depending on the card network and your contract terms.
  </Accordion>

  <Accordion title="What is CONDITIONAL_DECLINE and should I retry?">
    `CONDITIONAL_DECLINE` indicates a processing error or transaction timeout. It is technically a final status, but a payment may very rarely arrive for this transaction later (less than 1% of cases).

    **Recommended action:** Retry after some time. If you do retry, use a new `merchantUniqueId` — do not reuse the original. Before retrying, call Get Status with the original `merchantUniqueId` to confirm the original transaction did not succeed.
  </Accordion>
</AccordionGroup>

## Merchant Onboarding

<AccordionGroup>
  <Accordion title="What is the difference between PENDING_REVIEW and APPROVED?">
    - **`PENDING_REVIEW`** — The merchant has completed VKYC and DigiLocker. PayGlocal's compliance team is reviewing the submission. The merchant cannot yet process payments.
    - **`APPROVED`** — Compliance review passed. The merchant is fully activated and can process payments.

    `PENDING_REVIEW` is a normal intermediate state — no action required from you or the merchant. PayGlocal will notify you (via the onboarding status) when the review completes.
  </Accordion>

  <Accordion title="Can I update business details after the merchant acknowledges the T&Cs?">
    No. Business details and authorised signatory cannot be updated after T&C acknowledgement. If corrections are needed, contact [merchant.support@payglocal.in](mailto:merchant.support@payglocal.in) to reset the onboarding record.

    Bank details and beneficial owner information cannot be updated after the verification step is complete.
  </Accordion>

  <Accordion title="What happens if the VKYC fails?">
    If VKYC fails, the onboarding status moves to `RFI` (Request for Information). PayGlocal will specify what additional data or re-verification is needed.

    Check the status response for `rfiDetails` to understand what is required, then work with the merchant to provide the missing information.
  </Accordion>

  <Accordion title="Can I use the same externalOnboardingId for multiple merchants?">
    No. The `externalOnboardingId` must be **unique per merchant** in your system. It is your internal mapping from a PayGlocal `onboardingId` to your own merchant record. Reusing it will result in a `400 Bad Request` error.
  </Accordion>
</AccordionGroup>

## Key Management

<AccordionGroup>
  <Accordion title="I lost my Private Key. What do I do?">
    PayGlocal does not store your Private Key — once you navigate away from the download page, it cannot be recovered.

    If you have lost your PVT-KEY:
    1. Log in to the PayGlocal Control Center.
    2. Navigate to **Key Management → API Keys**.
    3. Create a **new key pair**.
    4. Download the new Private Key.
    5. Update your integration with the new key and KID.
    6. Deactivate the old key once the new one is confirmed working.
  </Accordion>

  <Accordion title="Can I use the same keys for UAT and Production?">
    No. Keys are environment-specific. UAT keys only work with UAT APIs (`api.uat.payglocal.in`) and Production keys only work with Production APIs (`api.prod.payglocal.in`). Download keys from each environment's Control Center separately.
  </Accordion>
</AccordionGroup>

## Still Stuck?

Contact the PayGlocal integration support team at [merchant.support@payglocal.in](mailto:merchant.support@payglocal.in) with:
- Your Merchant ID (MID)
- The GID or `externalOnboardingId` for the affected transaction/onboarding
- The full request (redact card numbers) and response you received
- The timestamp of the request
